# Locentra Cloudflare backend migration

**Status: local implementation and selected physical-device workflows completed. Production deployment and live service changes have not been made.** This document is the requested architecture entry point; the detailed callable-by-callable table remains in [CLOUDFLARE_FUNCTIONS_MIGRATION.md](CLOUDFLARE_FUNCTIONS_MIGRATION.md).

## Target architecture

- Flutter Android remains the client. Firebase Authentication (email/password) and Cloud Firestore remain on Spark.
- A new, separately named Cloudflare Worker handles trusted backend routes, App Check, Firebase ID token validation, authorization, Firestore REST transactions, and the media gateway workflow.
- Cloudflare R2 Standard holds media. The current Locentra quota remains 9,000,000,000 bytes. Panorama detection, blur, derivative processing, and 48-direction owner review remain on device.
- The Worker uses `workers.dev` initially. It requires no custom domain. The existing `locentra-upload-gateway` and `locentrastorage` resources are not this trial and must remain untouched.

## Migration state

- The Worker contains route implementations for the functions listed in the mapping, an idempotent profile bootstrap endpoint, account deletion, per-request Firebase account status/revocation validation, admin storage operations, and local emulator configuration.
- The Admin screen's quota, reconciliation, and orphan-deletion controls use the shared Firebase API wrapper, which dispatches to these Worker routes when `LOCALSPOT_BACKEND_URL` is configured. The old Functions fallback remains available when the Worker URL is absent. On the Infinix X6873, the Worker-backed quota screen loaded successfully and displayed the reconciled local ledger (48,506,129 bytes used, 0 reserved, no pending, failed, orphaned, or missing objects). Reconciliation and orphan deletion controls were not invoked in that UI check.
- The Flutter gateway now exposes safe media-asset deletion through the same Worker-or-legacy-callable dispatcher. The backend rejects deletion while an asset is still linked to a product, store, or tour; this adds the client API path but does not add a new media-management screen.
- Account deletion now includes every panorama derivative revision recorded beneath the user's media asset, uses quota-aware R2 deletion for each object, and marks the revision metadata deleted. The legacy Function fallback has the same cleanup behavior. Focused Worker unit tests cover owner-prefix filtering and Firestore subcollection pagination.
- Media deletion claims now transactionally re-read ownership and all product/store/tour link fields before setting `status=deleting`. The same race protection is present in the retained Firebase Function fallback; a linking transaction that wins the race causes deletion to abort before any object is removed.
- Panorama derivative SHA-256 verification now uses the R2 Worker binding's streaming `put()` integrity checksum. The gateway supplies the digest from the signed upload capability; R2 rejects a byte mismatch while streaming, and the backend compares R2's stored checksum from `HEAD` without buffering the derivative. The gateway also checks the JPEG end marker using a two-byte streaming tail, preserving the former full-file format check. Original panorama uploads likewise rely on the gateway's streaming signature and length checks instead of a full backend read. Product/store images still buffer up to their existing 8 MiB processing limit.
- Emulator Auth lookup now preserves the verified email/display-name claims for Worker profile bootstrap, and registration passes the selected display name. Concurrent bootstrap creation collisions now recognize Firestore REST status codes and return the already-created profile; an isolated Auth/Firestore integration regression passed with two simultaneous bootstrap requests, and Worker typecheck passed. Firestore transaction handling retries transient `ABORTED` and lock-contention conflicts with bounded jittered backoff; this fixes observed local emulator concurrency failures for quota reservations.
- Flutter opts into migrated callables and media flows only when `LOCALSPOT_BACKEND_URL` is set. Otherwise legacy Firebase Functions code paths remain. The Auth user-created Function also remains in source.
- Trial release startup now requires an explicit `LOCALSPOT_TRIAL_RELEASE=true` flag and a remote HTTPS Worker hostname in `LOCALSPOT_BACKEND_URL`. It rejects local/LAN hostnames, IP addresses, and HTTP, so a trial release cannot silently use the retained Functions fallback. Read-only preview remains a separate mode.
- Expired-media cleanup runs every 15 minutes as a resumable batch (up to five candidate records and two R2 objects per invocation). Full storage reconciliation is admin-triggered because its whole-inventory scan has not been proven to fit the Free Cron CPU ceiling.
- Panorama publication is not cleared for production: the Worker checks identity, hash, size, accounting, and owner attestation, but an owner attestation does not prove that image pixels are privacy-safe.

Firestore OAuth hardening fixes the JWT audience and token exchange to Google's token endpoint, rejects a non-Google token_uri in the service-account secret, and omits the optional delegated-subject claim and rejects credentials whose project_id differs from the Worker project. Unit regressions confirm the expected scope/audience and that no assertion is sent to an alternate endpoint. Firebase's current documentation confirms Firestore REST accepts Google OAuth 2.0 service-account tokens and applies IAM authorization, and lists Cloud Firestore's no-cost quota on Spark ([Firestore REST authentication](https://firebase.google.com/docs/firestore/use-rest-api), [Firebase pricing plans](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans)). On 2026-11-17, a dedicated project (`locentra-spark-trial-20261117`) was created without a billing prompt; its Standard Firestore database was provisioned in `asia-southeast1` (Singapore), with delete protection enabled. A read-only Firebase CLI database listing confirmed `databaseEdition: STANDARD`, `freeTier: true`, and `DELETE_PROTECTION_ENABLED`. With no billing association made, a dedicated service account and custom role were created using only `datastore.databases.get` and `datastore.entities.{create,delete,get,list,update}`. A temporary JSON key was held in process memory and deleted after testing; the actual OAuth exchange and Firestore transaction, create, read, query, and delete all passed against that project. The Cloud Billing API remains disabled, so a separate billing-status API query was not available; no billing account was linked during this work, and Spark status must be confirmed before any release. On 2026-11-17, the isolated project was also given an Android app named Locentra Android Trial (`app.locentra.mobile`, Firebase App ID `1:295175740638:android:5c69d12e29c215ca51f64f`) and its email/password Auth provider was enabled with `firebase deploy --only auth`; the local Auth config keeps anonymous sign-in off and does not enable phone/SMS. A disposable `example.invalid` account completed Auth REST sign-up and password sign-in, then was deleted successfully. The Android SDK config is selected by the `trial` Gradle flavor at `android/app/src/trial/google-services.json`, and separate Dart options in `lib/firebase_options_trial.dart` are selected only when `LOCALSPOT_TRIAL_RELEASE=true`. The `local` flavor is the default and `preview` retains its existing Firebase project. Play Integrity App Check remains unconfigured. Local emulator configuration now fails closed on public hosts and serves only localhost/private-LAN clients, reducing the risk of accidentally deploying the local configuration; public workers.dev hosts are rejected while localhost and private-LAN testing remain available. The emulator-backed Vitest suite runs with a single worker at a time because integration files mutate shared emulator collections and quota state.
